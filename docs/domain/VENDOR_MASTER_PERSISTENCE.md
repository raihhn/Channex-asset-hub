# Vendor master — local database slice

## Model

Vendor identity is separate from physical warehouses and operational PIC contacts. Ofsorts is one Vendor (`name=Ofsorts`, `legalName=Orang Seni Sejahtera`) with Jakarta and Jatim warehouses. Dua Garis Imagi is one Vendor with Jabar, Jogja, Semarang, Jatim and Lampung warehouses, as confirmed by the user. A vendor name is unique ignoring case and outer whitespace. Warehouse names are unique within a vendor. Do not parse parenthesized names at runtime or infer corporate identity from an address.

`vendor_master.vendors` owns stable UUID, display name, optional legal company name, active flag, version and timestamps. `warehouses` belongs to a Vendor and owns name, a free-text `text` address, confirmation marker and active flag. `contacts` belongs to a Vendor and owns PIC name, phone (text, retaining leading zeros), email and active flag. `warehouse_contacts` allows multiple PICs per warehouse and one PIC shared across warehouses; composite FKs prevent linking contacts from another Vendor. PIC is operational contact information, not an authenticated Person or app login.

`audit_events` records imports/creates/updates with actor, timestamp, version and changed-field names in the same transaction. It does not duplicate full contact payloads. Existing records are inactivated, not deleted. Updates lock the Vendor and check version to reject stale edits atomically. All reads/writes use the server repository; browser code never connects to PostgreSQL directly.

## Local operation

Use the existing local PostgreSQL URL in `ASSETHUB_DATABASE_URL` and set the server-only `ASSETHUB_VENDOR_ENABLED=true`. Run `npm run db:vendor:migrate` or `npm run db:vendor:seed`. The latter imports the initial two vendors, seven warehouses and two shared PIC records, without overwriting any existing Vendor on subsequent runs. The two clipped addresses (Ofsorts Jakarta and Dua Garis Imagi Jatim) use explicitly marked dummy text. Other addresses were transcribed from the supplied screenshot; the user supplied the full Jogja address. Confirmation markers describe completeness of the supplied data, not geocoding or physical verification.

Super Admin manages the records at `/admin/warehouses-vendors`: search, create/edit Vendor, add/edit warehouses, add/edit contacts, link multiple PICs and activate/inactivate records. The directory leads with vendor name, optional legal name, status and warehouse/PIC counts. Warehouse addresses and deduplicated PIC contacts live inside a closed disclosure per vendor; incomplete-address counts remain visible in the summary. Editing focuses on the form and hides the directory until saved/cancelled. The editor follows Vendor → Warehouse → PIC: create the warehouse name/address first, then select an existing vendor contact or add a completed PIC through a focused dialog within that warehouse. There is no preceding global PIC-entry section. New PICs are assigned to the initiating warehouse and can be reused by other warehouses without duplicating their contact record. Matching phone (including Indonesian +62/0 normalization) or email offers explicit reuse, never automatic merging by name. Different people sharing contact details require an explicit acknowledgement. Shared contact edits explain the affected warehouse count and apply to the single contact record. New warehouses prepend to the form, and unsaved-record deletion retains its confirmation dialog. Editor active states use labelled Switch controls; warehouse PIC assignments and address confirmation use Checkboxes with explanatory text. Status/assignment changes take effect only on Save vendor. Primary white inputs distinguish editable fields from secondary card surfaces using existing shared field tokens. Inactive PICs cannot be newly assigned, but existing assignments can be unchecked. Existing internal warehouse references remain view-only inside a separate closed disclosure. No automatic deletion, corporate grouping inference, procurement or commercial contracts are introduced.

API: `GET/POST /api/vendors`, `PUT /api/vendors/:id` with `{draft,version}`, and `GET /api/vendors/:id` for recent audit events. Input is validated on the server; duplicate names, foreign record reuse and stale edits fail without partial writes. Contact data is restricted to Super Admin on reads as well as writes. UI role visibility is a usability aid.

## Explicit boundaries

This is real durable **local PostgreSQL** storage. Supabase remains the accepted future managed provider per ADR 001; no cloud project or Supabase Auth has been configured. The temporary `x-prototype-actor-id` bridge only accepts an allowlisted active Super Admin fixture and is limited to a loopback database and localhost requests; this is not verified authentication. Cross-origin requests are denied. The private schema has no browser-role grants/policies, and RLS is enabled. Replace the prototype actor bridge with verified identity and deliberate server authorization before public deployment. Do not enable this API remotely as an auth shortcut.

New Request and Transfers destinations now use the persisted Vendor/warehouse UUIDs through the operational read projection described below. Existing historical fixture references remain readable and are never guessed or remapped to an unrelated real Vendor. A revision that still selects a legacy Vendor destination must choose a current database warehouse. Maintenance, reporting and People Vendor associations remain separate legacy prototype boundaries. The durable vendor audit is visible within the vendor editor, separate from the in-memory global prototype Audit Trail.

## Verification

Run `npm run typecheck`, `vitest run tests/vendor-master.test.ts`, and `ASSETHUB_VENDOR_TEST_DATABASE_URL=postgresql://localhost:54329/assethub_test npm run test:vendor:db`. Database tests require that isolated loopback test database and clean up only their own created IDs. Test creation, update, refresh, shared/multiple PICs, duplicate names, stale versions, rollback, foreign PIC FKs and unauthorized/cross-origin calls. Inspect desktop/mobile directory and editor. Never run these tests against user data.

## Request and Transfers connection

`GET /api/vendor-locations` permits an allowlisted active prototype Person to read only operational destination fields: warehouse UUID, Vendor UUID/name, warehouse/address label and linked active PIC contact text. It exposes neither inactive/incomplete records nor import/audit/admin fields. Vendor and warehouse must be active, address confirmed and at least one linked PIC active. The same local-only/origin/actor constraints apply; master-data reads/writes remain Super Admin-only.

The provider loads this projection on route changes and window focus. Internal warehouses/Stores remain fixture references; vendor fixtures are removed from all new Request/Transfer destination options. Network/configuration failures display an error and never fall back to old demo vendors. Selecting a vendor warehouse supplies its exact address and PIC suggestion; the operational PIC remains distinct from the requester/recording actor. Both warehouse and Vendor UUID are retained in Request and fulfillment groups. Request submit and Transfer plan/dispatch re-fetch current eligibility. Durable booking revalidates Vendor/warehouse associations inside its PostgreSQL transaction, with shared row locks against master updates.

TransferPlan stores a destination snapshot alongside warehouse UUID. Tracking, dispatch validation and physical receipt consume that snapshot; legacy plans without snapshots may resolve their original fixture IDs for history. Dispatch revalidates a database destination; receipt of an already-dispatched transfer retains its known snapshot even if the master is later changed. No import maps ABC Production or other demo vendors to real companies without evidence. Transfer execution remains in-memory prototype state; this connection establishes real Vendor master data, not durable transfer execution or production authentication.
